# T4 — Breakout

Using the VESPER-16 dev kit in this folder (`bin/vesper`), write a small playable Breakout game.
All positions below are as they appear in the PNG frames (column 0 = left, row 0 = **top**).

**Screen**
- Black (`#000000`) background. Nothing is drawn except the bricks, the paddle and the ball.
- **Bricks:** 3 rows of 8 bricks. Every brick is 7 pixels wide and 2 pixels tall. Brick *n* of a
  row (n = 0…7, from the left) covers columns 8n to 8n+6; column 8n+7 stays black, so the
  bricks are separated by 1-pixel gaps (the last column of the screen, 63, is a gap too).
  - top row: red (`#E8333A`), rows 4–5
  - middle row: orange (`#FF8C1A`), rows 8–9
  - bottom row: yellow (`#FFD93D`), rows 12–13
- **Paddle:** sky blue (`#3FA9F5`), 8 pixels wide and 1 pixel tall, in **row 46**. At the start
  it covers columns 28–35.
- **Ball:** a single white (`#FFFFFF`) pixel.
- The very first frame (`frame_0000.png`) already shows the full wall, the paddle at its start
  position and the ball resting on it.

**Paddle**
- While **LEFT** is held the paddle moves 1 pixel left per frame; while **RIGHT** is held it moves
  1 pixel right per frame. It always stays fully on screen (its left end stays within columns 0–56).
- The paddle moves in the same frame in which the button is held, before the ball moves.

**Serving**
- At the start, after a lost ball and after a cleared level, the ball **rests on the paddle**: it
  sits in row 45, directly above the paddle's 4th pixel from the left (start: column 31). While
  resting it moves along with the paddle and ignores everything else.
- The ball is served in the first frame in which **A** is held while it rests: in that same frame
  it moves one pixel up and one pixel right (start: from column 31, row 45 to column 32, row 44).
  A has no effect while the ball is in play.

**Ball in play** — every frame the ball moves exactly 1 pixel horizontally and 1 pixel vertically,
in this order:
1. Horizontal step. If it would leave the screen on the left or right, its horizontal direction
   reverses first and it moves the other way (so it is in column 0 or 63 for one frame, then moves
   away).
2. Vertical step, checked at the ball's new column:
   - If it would leave the screen at the top, its vertical direction reverses and it moves down
     instead (it is in row 0 for one frame).
   - If the pixel it would move into belongs to a brick, that brick is destroyed (the whole 7×2
     brick disappears in this frame), the vertical direction reverses and the ball moves one row
     the other way instead of entering the brick. Example: ball in row 14 moving up, the pixel above
     it in its new column is yellow → the brick disappears and the ball is now in row 15, moving
     down. Gaps between bricks and destroyed bricks do not stop the ball.
   - If it would move into row 46 and the paddle covers the ball's new column, it bounces the same
     way: it moves up to row 44 instead.
   - If it would move below the bottom row (row 47), the ball is **lost**: in this same frame it
     is back resting on the paddle, waiting for A. The bricks stay as they are. There are no lives;
     the game simply continues.

**Level cleared** — when the last brick is destroyed, in that same frame all 24 bricks are back and
the ball rests on the paddle (wherever the paddle is), waiting for A again. Play goes on like this
forever.

Buttons are supplied with `--input`. Save the program as `solutions/T4.vsa`. It must
run with e.g.

```
bin/vesper run solutions/T4.vsa --frames 1200 --input keys.txt --out out/T4
```

and print `OK 1200 frames`. We will play-test it with our own key sequences (including playing
until the wall is cleared), so try several input files yourself and check the frames before you
say you're done.
